Fundamentos de Calidad

Conceptos, métricas y estándares utilizados para evaluar la calidad del software.

¿Qué es la calidad de software?

La calidad de software es el conjunto de características que permiten determinar si un sistema cumple con los requisitos establecidos y satisface las necesidades de sus usuarios.

Para evaluar la calidad se utilizan diferentes métricas, que permiten medir aspectos como rendimiento, seguridad, mantenibilidad y confiabilidad.

  • Confiabilidad: capacidad del sistema para funcionar correctamente.
  • Usabilidad: facilidad de uso y aprendizaje.
  • Eficiencia: utilización adecuada de los recursos.
  • Seguridad: protección de datos y acceso al sistema.
  • Mantenibilidad: facilidad para modificar y corregir el software.

Estándares de calidad

ISO 9126

La norma ISO 9126 define un modelo de calidad para evaluar diferentes características de un producto de software.

Funcionalidad

Capacidad de cumplir las funciones requeridas.

Confiabilidad

Capacidad de mantener un funcionamiento correcto.

Usabilidad

Facilidad de aprendizaje y utilización.

Eficiencia

Relación entre rendimiento y recursos utilizados.

Mantenibilidad

Facilidad para analizar y modificar el software.

Portabilidad

Facilidad para trasladar el software a otros entornos.

ISO/IEC 25000

La familia ISO/IEC 25000, conocida como SQuaRE, establece un conjunto de normas para especificar, medir y evaluar la calidad de productos de software.

Calidad del producto

Permite evaluar las características y propiedades del software.

Calidad en uso

Analiza el resultado del uso del software en un contexto determinado.

Medición

Define métodos y métricas para evaluar diferentes características de calidad.

Evaluación

Permite establecer criterios para determinar la calidad del producto.

Procesos de Desarrollo de Software

Cómo se organiza el trabajo, de la idea al software en producción

El ciclo de vida del desarrollo (SDLC) y los modelos tradicionales que durante décadas definieron cómo un equipo transforma requisitos en software funcionando.

Ciclo de vida del desarrollo (SDLC)

Las seis etapas por las que atraviesa todo proyecto de software.
01

Requisitos

Se relevan las necesidades del cliente y del negocio.

02

Diseño

Se define la arquitectura y el comportamiento del sistema.

03

Desarrollo

Se escribe el código que implementa lo diseñado.

04

Pruebas

Se verifica que el software cumpla lo requerido.

05

Despliegue

El software pasa a producción y queda disponible.

06

Mantenimiento

Se corrigen errores y se agregan mejoras post-lanzamiento.

Modelos tradicionales

Tres formas clásicas de estructurar el SDLC, cada una con sus propios trade-offs.

Modelo en cascada

Cada etapa del SDLC se completa por entero antes de comenzar la siguiente, en una secuencia lineal sin retroceso.

Diagrama del modelo en cascada y sus etapas.

Pruebas

Ventajas

  • Estructura simple y fácil de planificar
  • Documentación clara en cada etapa
  • Funciona bien con requisitos estables

Desventajas

  • Poca flexibilidad ante cambios
  • El cliente ve resultados muy tarde
  • Los errores de diseño se detectan tarde
Cuándo usarlo: proyectos con requisitos bien definidos y estables desde el inicio, y bajo riesgo de cambio.

Modelo en V

Extiende la cascada asociando cada etapa de desarrollo con una etapa de prueba equivalente, verificando desde el principio.

Diagrama del modelo en V y la relación entre desarrollo y pruebas.

Requisitos ↔ Pruebas de aceptación
·
Diseño ↔ Pruebas de sistema
·
Código ↔ Pruebas unitarias

Ventajas

  • La verificación se planifica desde el inicio
  • Detecta errores de diseño más temprano
  • Buena trazabilidad entre requisito y prueba

Desventajas

  • Sigue siendo rígido ante cambios
  • Poco espacio para prototipado temprano
  • Requiere requisitos muy detallados
Cuándo usarlo: proyectos donde la confiabilidad es crítica (sistemas médicos, aeroespaciales) y el costo de un error es alto.

Ventajas

  • Entrega valor funcional desde etapas tempranas

  • Reduce el riesgo de grandes fallas al final

Desventajas

  • Requiere una arquitectura pensada para crecer
  • Puede ser difícil de planificar y presupuestar
  • Exige comunicación constante con el cliente
Cuándo usarlo: proyectos con requisitos que pueden evolucionar, o cuando se necesita mostrar avances tempranos. Es la base conceptual de las metodologías ágiles.
Metodologías Ágiles

Entregar valor en ciclos cortos y adaptarse al cambio

Los valores del Manifiesto Ágil, Scrum, Kanban y XP explicados con esquemas y herramientas interactivas, y comparados con los modelos tradicionales.

El Manifiesto Ágil

Nació en 2001, cuando 17 profesionales criticaron los modelos basados en procesos pesados.
Valor 1

Personas sobre procesos

Los procesos y las herramientas ayudan, pero el talento y la interacción del equipo pesan más.

Valor 2

Software que funciona

Se prioriza el producto operativo; la documentación se reduce a lo que aporta valor.

Valor 3

Colaboración con el cliente

El cliente acompaña al equipo en lugar de limitarse a lo pactado en un contrato inicial.

Valor 4

Respuesta al cambio

Adaptarse es más valioso que seguir un plan cerrado, sobre todo si los requisitos cambian.

Frente a lo tradicional: la gestión predictiva (cascada, modelo en V) busca cumplir plazos, costos y alcance fijados de antemano. La agilidad parte de un mínimo viable y lo hace crecer con feedback continuo.

Scrum

Un marco ágil con sprints de duración fija, roles claros y reuniones breves.

El nombre viene del rugby: el equipo avanza junto, empujando en bloque. En Scrum el trabajo se organiza en sprints (no más de 4 semanas), y cada uno termina con un incremento listo para entregar.

Roles

Los actores principales que participan y estructuran el marco de trabajo en Scrum.
Rol

Propietario del producto

Representa al cliente, es una sola persona y decide el orden de la pila del producto. Su responsabilidad es el valor del producto.

Rol

Desarrolladores

Entre 3 y 9 profesionales multifuncionales que se autogestionan y comparten la responsabilidad de construir el incremento.

Rol

Scrum master

Garantiza que se cumplan las reglas del marco, modera el scrum diario y resuelve los impedimentos del equipo.

Artefactos

Elementos de información diseñados para definir el trabajo y su valor.
Artefacto

Pila del producto

Lista priorizada y viva de requisitos, normalmente escritos como historias de usuario. La administra el propietario del producto.

Artefacto

Pila del sprint

Tareas necesarias para cumplir el sprint, de un día o menos cada una. Solo los desarrolladores la modifican.

Artefacto

Incremento

Parte del producto terminada, probada y operativa al final del sprint. No cuentan los prototipos ni lo pendiente de pruebas.

Kanban

Un flujo continuo y visual, sin sprints de duración fija.

El equipo coloca tareas en un tablero y su columna indica su estado. El límite WIP (work in process) fija cuántas tareas pueden estar a la vez en una etapa, para evitar cuellos de botella.

Probá el tablero

Arrastrá las tarjetas o usá los botones para moverlas entre las columnas. Recordá que «En curso» admite un máximo de 3 tareas.

Pendiente

En curso

Terminado

Ventajas

  • Se adapta a trabajo que llega de forma continua.
  • Muestra cuellos de botella.
  • No exige reuniones ni roles propios.

Desventajas

  • Sin plazos fijos, puede haber demoras por perfeccionismo.
  • Requiere disciplina para respetar el WIP.
  • Sin sprints, hay menos hitos de revisión.

Extreme Programming (XP)

Un conjunto de prácticas técnicas para lograr software de calidad, propuesto por Kent Beck.

XP lleva al extremo buenas prácticas de ingeniería: ciclos muy cortos, pruebas constantes y comunicación directa. Se combina con frecuencia con Scrum.

Práctica

Programación en pareja

Dos personas trabajan juntas en una tarea; una escribe y la otra revisa en el momento.

Práctica

Desarrollo guiado por pruebas

Primero se escriben los tests (TDD) y después el código que debe pasarlos.

Práctica

Integración continua

El código se integra y se prueba varias veces al día para detectar errores enseguida.

Práctica

Refactorización

Se mejora la estructura del código sin cambiar su comportamiento, para mantenerlo simple.

Práctica

Entregas pequeñas

Versiones frecuentes y funcionales, para recibir feedback del cliente cuanto antes.

Práctica

Propiedad colectiva

Cualquier integrante puede modificar cualquier parte del código.

Preguntas frecuentes

Resolvé tus dudas sobre la calidad del software.

Es el grado en que un sistema cumple los requisitos explicitos y las expectativas implícitas: que sea funcional, confiable, facil de usar y de mantener.

ISO 9126 definió un modelo de características de calidad. La familia ISO/IEC 25000 (SQuaRE) lo actualiza y amplia, e incluye evaluación y medición.

Es un conjunto de estándares internacionales que establecen criterios y recomendaciones para mejorar la calidad de productos y servicios.

ISO 25010 es una versión más actualizada que reemplazó a ISO 9126, incorporando nuevos criterios para evaluar la calidad del software.

El modelo Cascada conviene cuando los requisitos están definidos desde el inicio y no se esperan muchos cambios. En cambio, el modelo Ágil es mejor cuando el proyecto necesita flexibilidad, cambios frecuentes y entregas progresivas.

No, Scrum y Kanban no son lo mismo. Ambos son métodos ágiles, pero Scrum organiza el trabajo en períodos cortos llamados sprints, mientras que Kanban utiliza un tablero visual para organizar las tareas y controlar su avance de forma continua.

Un equipo Scrum suele tener 10 personas o menos, incluyendo al Scrum Master, Product Owner y Developers. Lo importante es que sea un equipo pequeño, organizado y capaz de trabajar de forma autónoma.

Ejercicios y casos prácticos

Pensá tu respuesta antes de mostrar la solución.

Clasificá la prueba

Fácil

Un equipo prueba el formulario de registro ingresando datos y comprobando solo lo que muestra la pantalla, sin mirar el código. ¿Qué tipo de prueba es y a qué nivel corresponde?

Solución:

Es una prueba de caja negra porque se evalúa el comportamiento sin revisar el código. Corresponde al nivel de sistema si se comprueba el proceso completo de registro.

Elegí el modelo

Fácil

Un hospital desarrolla software de monitoreo cuyo costo de error es muy alto y cuyos requisitos están muy detallados. ¿Qué modelo tradicional le conviene?

Solución:

El modelo en V, porque permite planificar actividades de verificación y validación para cada etapa del desarrollo. Es adecuado para proyectos críticos que necesitan controles y pruebas rigurosas.

Armá el sprint

Medio

Un equipo tiene una historia grande: «el usuario puede gestionar su perfil». ¿Qué debería hacer en la planificación del sprint?

Solución:

Dividir la historia en tareas o historias más pequeñas, definir criterios de aceptación y seleccionar una cantidad de trabajo que el equipo pueda completar durante el sprint.

Respetá el WIP

Medio

Un tablero Kanban tiene WIP=3 en «En curso» y ya hay 3 tarjetas. Llega una urgencia. ¿Qué se hace?

Solución:

No se debe agregar otra tarea sin más. Primero hay que intentar terminar o liberar una tarea en curso. Si la urgencia requiere prioridad, el equipo debe aplicar una política de excepción acordada.

Detectá el error

Difícil

Un equipo hace Scrum con sprints de 3 semanas, pero la retrospectiva se usa para mostrar el producto al cliente. ¿Qué está mal?

Solución:

Se están confundiendo dos eventos. La revisión del sprint sirve para mostrar el incremento y recibir comentarios. La retrospectiva se utiliza para analizar cómo trabajó el equipo y proponer mejoras.
